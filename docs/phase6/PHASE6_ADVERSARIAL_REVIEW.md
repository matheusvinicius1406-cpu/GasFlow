# FASE 6 — ADVERSARIAL REVIEW

## Methodology

Each scenario was tested with real code execution, not theoretical analysis.
Results: PASS, FAIL, or NOT VERIFIED with evidence.

---

## 1. Posso criar dois clientes com mesmo telefone?

**PASS** ✅

Evidence:
- `UniqueConstraint("telefone", name="uq_clients_telefone")` in client_model.py:40
- Test `test_unique_telefone_enforced_by_db` confirms IntegrityError on duplicate
- App-level check in `CreateClientUseCase` catches before DB (clean error message)

## 2. Posso fazer isso concorrente?

**PASS** ✅

Evidence:
- DB-level UNIQUE constraint is the safety net
- App-level check-then-insert is best-effort (race window exists)
- DB constraint guarantees exactly one succeeds
- Test `test_concurrent_duplicate_phone` confirms behavior

## 3. Posso alterar métricas?

**PASS** ✅

Evidence:
- `ClientCreate` schema has no `total_orders`, `total_spent`, etc. fields
- `ClientUpdate` schema has no derived fields
- `Customer360Response` is read-only (no write endpoint for metrics)
- Test `test_mass_assignment_create` and `test_mass_assignment_update` confirm

## 4. Posso alterar código?

**PASS** ✅

Evidence:
- `codigo` is not in `ClientUpdate` schema
- `codigo` is generated by `proximo_codigo()` — never from user input
- Test `test_mass_assignment_update` confirms `codigo` not in update dump

## 5. Cliente inativo perde histórico?

**PASS** ✅

Evidence:
- `ativo=False` is a soft delete — row preserved
- Orders have FK to `clients.codigo` — not to `ativo`
- Test `test_soft_delete_preserves_orders` confirms orders persist after disable
- Customer 360 still returns data for disabled clients

## 6. Posso criar pedido para cliente inexistente?

**PASS** ✅

Evidence:
- `ForeignKey("clients.codigo")` on OrderModel.client_codigo
- `PRAGMA foreign_keys = ON` enforced
- Test `test_order_requires_valid_client` confirms IntegrityError

## 7. Customer360 calcula errado?

**PASS** ✅ (with known gap)

Evidence:
- Metrics derived from `get_customer_metrics()` — single aggregation query
